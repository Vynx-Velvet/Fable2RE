Findings
- The host native renderer thread is the limiter in towns (81-88% of a core); the guest GameThread
  runs ~32% and spends ~22 ms/frame waiting for the renderer at Swap
  (native_render_frames_ahead = 0, kept for the Bink title video), so game and renderer do not overlap.
- "resolve" time is mostly not copying: the depth resolve runs RunDeferred (real-time shadow
  deferral replays the ~1,100 recorded scene draws plus a depth pre-pass). Draw + resolve =
  ~28 ms for ~3,200 draws, about 9 us per draw.
- Render thread profile (Bowerstone): ExecuteCmd self 12%, memmove+memchr 12%, NVIDIA driver ~12%,
  DrawInternal/RecordDraw/UpdateDrawConstants ~10%, XXH3 hashing 2.7%, std::map constant store 0.7%.
- Renderer "hitches" in towns (81 in Bowerstone, avg 58 ms) are heavy frames (3,500+ draws), not
  asset work; Oakfield also compiled 16 new pipelines (5.2 s total on async threads) and 206 textures.
- Debug.EngineConfig (EnableLightmaps, EnableShadows, DebugPage=...) is compiled out of retail: the
  string 'EngineConfig' is not in the XEX. Those debug menu entries cannot work.

Next steps (expected effect)
1. Overlap game and renderer: frames_ahead = 1 outside video playback (~42 -> ~36 ms, ~28 fps).
2. Per-draw cost: avoid per-draw command copies (ExecuteCmd/memmove/memchr) and hashing; target
   ~4 us/draw.
3. Measure native_realtime_shadows=false to price the deferral/pre-pass (up to ~12 ms).
4. Record command lists on several threads.

## Optimisation round 1 (2026-10-02 19:40, release build 19:41, awaiting user test)

Measured offline first (Fable2Replay on capture 20261001_231347, 3,050 draws incl. 855 pre-pass):
GPU wait at frame end < 1 ms -> the frame is CPU-bound; replay steady pass ~50 ms is dominated by
the replayer's own memory replay (Capture::Apply/UploadPhysical), so it is not a proxy for the
in-game renderer thread (11 us/draw in game vs 3.6 us in replay).
New replayer tools: per-pass timing (`pass N: ms (EndFrame ...)`, steady-state median), `--sample`
(in-process sampler, replay/sampler.h), `--profile` sections reset after warm-up.

Changes (all verified pixel-identical on the replay capture where the replayer exercises them):
1. Frame pipelining: native_render_frames_ahead default 1 (was 0); the renderer requests 60 frames of
   lockstep whenever textures were rewritten by the CPU in a frame (Bink video: ~3 per frame; town 0).
   Perf log: "lockstep swaps N%".
2. Recording side (game render thread): shader microcode interned by XXH3 (no per-draw copies of the
   loaded microcode; hash passed to the renderer = no re-hash in GetShader; deferred draws keep the
   pointer); device snapshots are deltas of changed 64-byte chunks (was ~3.4 KB per command, applied
   again on the renderer thread); Before-hook copy stops at the last field read (12704, not 16384).
3. Renderer thread wake-ups: the game thread notifies only when the renderer sleeps.
4. Real-time shadow deferral: per-draw constant file (9.4 KB) stored as 64-byte-block deltas against
   one base copy (was copied 3x per deferred draw, ~900 per frame).
5. Diagnostics: render_sampler now samples the native renderer AND the game's render thread and logs
   hot source lines; release toml: native_draw_profile = true, old cpu_sampler_thread disabled.

Expected: game thread no longer blocked ~13-16 ms/frame at Swap (pipelining) and ~5 ms of hook time
shrinks; frame = max(game, renderer) -> town ~28-32 fps. 60 fps still needs the renderer thread
under ~16 ms (multi-threaded command recording or per-draw state caching) and the game's own render
thread under ~16 ms (next profile shows where).
