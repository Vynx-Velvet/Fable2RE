# Project direction

Fable2RE aims to let anyone use their own Xbox 360 copy of Fable II to build a fully native, deeply moddable PC port. The desired source is readable C++ for the entire game, organized around recognizable systems, types, and behavior. Platform and middleware functionality should ultimately use suitable native implementations.

## What “fully native” means here

The finished port should not need a PowerPC register context, a big-endian guest address space, Xbox GPU command emulation, or console platform compatibility services to execute the game. Compiling translated instructions into a Windows executable is useful progress, but does not by itself meet this definition.

Our current build retains several of those dependencies. ReXGlue-generated functions establish a runnable baseline; automatic lifting makes them easier to inspect; reviewed replacements recover intent and structure. [Architecture](architecture.md) explains these separate stages.

## OpenGOAL as inspiration

[OpenGOAL](https://opengoal.dev/) emphasizes native execution, understanding original games, and enabling modifications. We share those priorities. Fable2RE targets C++ reconstruction of Fable II; it does not reuse OpenGOAL's language strategy or claim its level of completion.

## Relationship to other Fable II projects

**Separate projects can share a technical foundation while pursuing different visions.** Fable2RE and Himdo's Fable-2-Recomp both use ReXGlue. Shared tooling and similar generated game code do not establish that either project was forked from the other.

**They are different kinds of project.** A static recompilation turns the executable's machine code into C++ automatically at every build and runs it on a runtime that recreates the console; its goal is a game that runs well. Fable2RE is a source reconstruction, like [OpenGOAL](https://opengoal.dev/) for Jak and Daxter: the recompiled build is its reference, and its product is the game's own code, rebuilt function by function as readable C++, on native PC systems. How far that has come is counted in [conversion progress](progress.md).

External descriptions checked on 2026-10-15 (first on 2026-10-03). Projects evolve; this comparison describes documented approaches, not permanent limits on anyone else's work.

| Project | Documented approach / commitment |
|---|---|
| [Himdo/Fable-2-Recomp](https://github.com/himdo/Fable-2-Recomp) | Recompilation with ReXGlue: guest PowerPC code "statically recompiled to C++ at build time by `rexglue codegen`", with game patches (mid-asm hooks), a launcher with an ISO extractor, debug-menu and Lua functionality, renderer work and several language editions |
| Fable2RE | A transition from a recompiled baseline to readable whole-game C++ and native platform systems, comprehensive modding, and full Lionhead debug-tool restoration |

Static recompilation executes translated CPU code compiled ahead of time. It can still use runtime services descended from an emulator. These facts can coexist: “uses ReXGlue” does not mean “runs the CPU through Xenia's JIT,” and “builds a native executable” does not mean “has reconstructed the entire game into maintainable source.”

Fable2RE also relies on ReXGlue today. We credit that foundation while working toward replacing the remaining console-specific dependencies. Mod support, a debug menu, or a native renderer alone are not exclusive differentiators. The defining commitment is the scope of reconstruction and the final architecture.

### Source ancestry and the folder name

The local `Fable2Recomp/` tree originates from [Fable2Recomp/Fable2Recomp](https://github.com/Fable2Recomp/Fable2Recomp). It inherited application code, hooks, and build configuration, followed by this project's changes; that earlier Git history is kept by the maintainers outside this repository, and this repository contains the current files only. The directory name reflects that upstream foundation; it is not evidence of ancestry from Himdo's repository.

Keep three kinds of source distinct:

- **Generated game code:** ReXGlue produces translations locally from the user's executable and the codegen configuration. Similar output can result from the same inputs and tools without one project copying the other.
- **Inherited project code:** Application scaffolding, integration code, and configuration have their own authors and history. They are not all generated by ReXGlue, and their attribution remains part of Fable2RE.
- **Fable2RE development:** Readable replacements, native systems, research, and tools advance this project's reconstruction goals on top of that foundation.

Our verified relationship is therefore: Fable2RE builds on Fable2Recomp/Fable2Recomp and ReXGlue; Himdo's documentation confirms ReXGlue use. We have not established whether Himdo's project also inherits source from Fable2Recomp/Fable2Recomp, so we do not claim that additional shared ancestry. The local history reviewed does not identify Himdo's repository as Fable2RE's upstream.

## Reverse engineering with AI assistance

The project brings forward the team's reverse-engineering experience from FlyX and intends to use the most capable current models available for analysis and implementation. Model selection evolves with demonstrated results; this is a working approach, not a fixed benchmark ranking or a required paid toolchain.

Useful model-assisted tasks include tracing call chains, proposing structures, explaining decompiler output, writing transformation tools, and drafting C++ replacements. Every accepted result needs review against the executable, instruction-level references, and relevant behavior checks. Record uncertainty and reproducible evidence. A model's confidence or a successful compile does not establish behavioral equivalence.

## Full modding and debug restoration

The goal covers scripts, quests, combat, AI, UI, text, assets, rendering, and native engine behavior. Existing tools provide parts of that workflow; stable interfaces and complete content-format coverage remain work to do.

For Lionhead's debug menu, success means more than displaying the original labels. Surviving commands must be connected correctly, compiled-out functionality must be rebuilt where possible, and behavior must be verified. Missing retail code requires reconstruction, not simply flipping a flag. See [debug-menu status](debug-menu.md).
